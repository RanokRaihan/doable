## Critical

### C-1 — Unprotected Cloudinary signature endpoint ✅ Fixed

**File:** `src/app/api/cloudinary-signature/route.ts`  
**Related:** `src/proxy.ts:163` (middleware matcher)  
**Resolution:** Added `getCurrentUser()` check at the top of the `GET()` handler; returns 401 if unauthenticated.

The middleware matcher pattern explicitly excludes all `/api/*` routes from protection:

```ts
matcher: ["/((?!api|_next/static|_next/image|favicon.ico|...).*)"];
```

`GET /api/cloudinary-signature` is therefore reachable by any unauthenticated visitor. The handler returns a valid Cloudinary upload signature for the `doable/tasks` folder, including the `apiKey` and `cloudName`. Any external party can use this signature to upload arbitrary files to your Cloudinary account at your cost.

**Fix:** Add an auth check at the top of the route handler, or extend the middleware matcher to include this route. Simplest fix in the route:

```ts
// Inside GET() handler, before signing:
const user = await getCurrentUser();
if (!user) return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
```

### C-2 — `BACKEND_URL` string concatenation omits trailing-slash guard ✅ Fixed

**File:** `src/lib/auth/proxy-utils.ts:40`  
**Resolution:** Replaced template-literal concat with `new URL("api/v1/auth/refresh-token", env.backendUrl).toString()`.

```ts
const response = await fetch(`${env.backendUrl}api/v1/auth/refresh-token`, {
```

If `BACKEND_URL` is set without a trailing slash (e.g., `http://api.example.com`), this produces the malformed URL `http://api.example.comapi/v1/auth/refresh-token`. Token refresh silently returns `null`, so every user with an expiring access token is permanently logged out.

All other API calls use `buildUrl()` in `src/lib/api/utils.ts`, which uses `new URL("api/v1/...", BASE_URL)` and handles this correctly. `proxy-utils.ts` is the only outlier.

**Fix:**

```ts
const url = new URL("api/v1/auth/refresh-token", env.backendUrl).toString();
const response = await fetch(url, { ... });
```

## High

### H-1 — Server Action called from middleware (Edge Runtime incompatibility) ✅ Fixed

**File:** `src/proxy.ts:117`  
**Resolution:** Removed `setCookie` import; replaced with `response.cookies.set("unauthorizedAttempt", "true", { maxAge: 60, path: "/" })` on the redirect `NextResponse`.

```ts
await setCookie("unauthorizedAttempt", "true", { maxAge: 60 });
```

`setCookie` is a `"use server"` function (from `src/actions/common/cookie.ts`) that calls `cookies()` from `next/headers`. Middleware runs in the **Edge Runtime**; `next/headers` is not available there. This call either throws silently or sets the cookie in a context that is discarded. The `unauthorizedAttempt` cookie is never written, so the `/unauthorized` page cannot show the expected contextual message.

All other cookie writes in the same file correctly use `response.cookies.set()` on a `NextResponse` object.

**Fix:** Replace the Server Action call with direct response cookie mutation:

```ts
const response = NextResponse.redirect(new URL("/unauthorized", request.url));
response.cookies.set("unauthorizedAttempt", "true", { maxAge: 60, path: "/" });
return withRefreshedCookies(response);
```

### H-2 — `updateWithdrawalMethodValidation` schema does not match its intended contract ✅ Fixed

**File:** `src/schema/updateWithdrawalMethodValidation.ts`  
**Resolution:** Made all fields optional and added `.refine()` to enforce at-least-one-field-provided.

AGENTS.md documents this schema as "All fields optional; at least one required." The actual schema is the opposite — every field is required with `.min(1)` and there is no `.refine()` guard for at-least-one.

Consequences:

1. The edit form must re-submit all six fields on every save, even when only one is changing.
2. Empty `branchName` and `routingNumber` strings are sent to the PATCH endpoint, potentially clearing existing values on the backend.
3. The form cannot be used as a partial update.

**Fix:** Make fields optional and add the refine constraint:

```ts
const updateWithdrawalMethodValidation = z
  .object({
    methodType: z.enum(["BANK", "MOBILE_BANKING"]).optional(),
    accountName: z.string().min(1).max(100).optional(),
    accountNumber: z.string().min(1).max(50).optional(),
    bankName: z.string().max(100).optional().nullable(),
    branchName: z.string().max(100).optional().nullable(),
    routingNumber: z.string().max(50).optional().nullable(),
  })
  .refine((d) => Object.values(d).some((v) => v !== undefined), {
    message: "At least one field must be provided to update",
  });
```

### H-3 — `createWithdrawalMethodValidation` missing BANK-conditional rule for `bankName` ⏭️ Intentional

**File:** `src/schema/createWithdrawalMethodValidation.ts`  
**Decision:** `bankName` is intentionally required for all method types. Mobile Banking uses the provider name (e.g., "Bkash") in this field. No change needed.

AGENTS.md documents this file as "BANK cross-field rule: bankName required when methodType=BANK." The actual schema applies `z.string().min(1, "Bank name is required")` unconditionally for all method types. There is no `superRefine` or conditional check.

For `MOBILE_BANKING` methods, the form shows the field with a "Bkash"-style placeholder, so users will fill it in. But if the intent is that `bankName` should only be required for `BANK` type, the schema and form are wrong. Any MOBILE_BANKING submission where bankName is empty will fail validation.

**Fix:** Add a `superRefine` to enforce the rule conditionally:

```ts
const createWithdrawalMethodValidation = z
  .object({
    methodType: z.enum(["BANK", "MOBILE_BANKING"]),
    accountName: z.string().min(1).max(100),
    accountNumber: z.string().min(1).max(50),
    bankName: z.string().max(100).optional(),
    branchName: z.string().max(100).optional(),
    routingNumber: z.string().max(50).optional(),
    isDefault: z.boolean(),
  })
  .superRefine((data, ctx) => {
    if (data.methodType === "BANK" && !data.bankName) {
      ctx.addIssue({
        code: "custom",
        path: ["bankName"],
        message: "Bank name is required",
      });
    }
  });
```

### H-4 — `CancelWithdrawalRequestDialog` enforces min-10-char rule on a field labeled "optional" ✅ Fixed

**File:** `src/components/profile/withdrawal/requests/CancelWithdrawalRequestDialog.tsx:43-46`  
**Resolution:** Cancellation reason is required by design. Updated label to "Reason (required, min 10 characters)". Validation logic unchanged.

The UI label reads **"Reason (optional)"**, but `handleCancel` calls:

```ts
if (reason.trim().length < 10) {
  e.preventDefault();
  setError("Please provide at least 10 characters.");
  return;
}
```

This fires when the field is completely empty (`length === 0`), blocking every cancellation attempt unless the user types at least 10 characters. The API schema (`cancelWithdrawalRequestValidation.ts`) and the action both accept an absent/empty `cancellationReason`.

**Fix options:**

1. Remove the min-10 guard entirely (since cancellationReason is optional per API contract).
2. Allow empty but enforce min-10 only if something was typed: `if (reason.trim().length > 0 && reason.trim().length < 10)`.
3. Update the label to "Reason (required, min 10 chars)" if the min-10 rule is intentional.

### M-2 — `requireAuth()` hardcodes callback path as `/profile` ⏭️ Skipped

**File:** `src/lib/auth/requireAuth.ts:44-48`  
**Decision:** Skipped by design — middleware already handles the primary redirect with the correct callback URL.

```ts
function getCurrentPath(): string {
  // In Server Components, we can't easily get the current path
  return "/profile"; // ← always returns "/profile"
}
```

Any Server Component that calls `requireAuth()` without an explicit `callbackUrl` will redirect an unauthenticated visitor to `/login?callbackUrl=/profile` regardless of the actual page. After login the user lands at `/profile` instead of the page they were trying to visit.

The middleware handles the primary auth redirect with the correct callback URL, so this doesn't cause a security gap, but it breaks the UX for any Server Component that triggers `requireAuth()` independently (e.g., deep-link access).

**Fix:** Pass `headers()` to reconstruct the path, or always pass an explicit `callbackUrl` at every call site.

### M-3 — `logoutAction` does not call a backend logout endpoint ✅ Fixed

**File:** `src/actions/auth/authAction.ts:60-63`  
**Resolution:** Added best-effort `POST /auth/logout` call before `clearTokens()`. Local cookies are cleared regardless of backend response.

```ts
const logoutAction = async () => {
  await clearTokens();
  return { success: true };
};
```

Only local cookies are deleted. The issued JWT access token continues to be valid on the backend until its `exp` claim is reached (up to 15 minutes, configurable via `ACCESS_TOKEN_MAX_AGE`). If the backend exposes a logout endpoint that invalidates the token or refresh token server-side, it is not being called.

**Fix:** Call the backend logout endpoint (e.g., `POST /auth/logout`) before clearing local cookies. If no such endpoint exists, document this limitation explicitly.
